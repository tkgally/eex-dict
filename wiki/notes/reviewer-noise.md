# [tooling] reviewer-a: originality-check questions answered "copied" 10/10

*Originality run, 2026-09-19 (`20260919T070307Z-41gmqe`), `tools/originality_check.py sample --n 10`.*

The originality-check reviewer question ("does this definition read as copied from a published dictionary, or original?") was put to reviewer-a for all 10 sampled definitions, each in one combined call, without naming a source. reviewer-a answered "copied" for all 10, citing only that the wording was "polished," "characteristic," or "standard" dictionary-style phrasing — never a specific matching source or phrase. An exact-phrase web search found no published match for any of the 10. On the session's own reading against recalled published-dictionary wording, 3 of the 10 looked like real paraphrases of a specific dictionary's distinctive sentence shape (`be-v` `be-that-as-it-may`, `please-interj` sense 3, `person-n` `in-person`) and were rewritten; the other 7 were short, closed-vocabulary definitions that any learner dictionary would phrase similarly (`generic-overlap`).

A 100 percent "copied" rate with no source cited, 70 percent of it unsupported by search evidence, suggests this reviewer role over-triggers on concise, controlled-vocabulary phrasing per se rather than on genuine resemblance to a specific source. The originality check's own verdict (`generic-overlap` vs `rewrite`) should keep resting on the session's reading plus the exact-phrase search, not on this reviewer's answer alone. Not yet enough originality-check runs (one so far) to size a fix; re-check at the next forced originality run (every 10th) and, if the pattern repeats, consider dropping the reviewer question from this checklist in favor of the search alone.

**Update, 2026-09-20** (`20260920T033331Z-pnzdne`): the second forced run put the same question to reviewer-a for a fresh sample of 10. This time the answers were mixed — 4 copied, 4 original, 2 cannot tell — not the earlier 100 percent "copied." Still no specific source cited for any "copied" verdict. Nine of the ten were settled by the exact-phrase search plus the session's own reading (`reviews/originality/2026-09-20.md`); one genuine near-match turned up independently (a Macmillan Dictionary synonym-list entry, found by search, not flagged by the reviewer) and was rewritten. The 100 percent rate does not look like a stable pattern after two runs; keep the reviewer question for now, keep resting the verdict on search plus the session's reading, and re-check again at the next forced run before deciding whether to drop it.

## [tooling] reviewer-a fixated on one field across four straight review-panel rounds

*Closure run, 2026-09-21 (`20260921T003323Z-93ipdt`), `surround-v`'s `core_idea`.*

Four consecutive `review_panel.py surround-v` calls each drew a blocking complaint from reviewer-a about the entry's `core_idea`, and each complaint gave a different, sometimes self-contradicting reason: round 1 said the infinitive construction itself was wrong (contradicted by `add-v`'s already-approved core idea, which uses the same "To **add** is to..." form) and that the sentence treated feelings as things that surround; round 2, after a reword, said the explanation's illustration reversed subject and object (checked against the actual example sentence, it had not); round 3, after another reword, said the sentence was "ungrammatical" because the subject was described as "being placed" rather than "placing" — the opposite complaint from round 1's framing, and not accurate either (surround's subject is the thing that gets placed around the target, which is exactly what the wording said). reviewer-b never once flagged `core_idea` in any of the four rounds. Two rounds of genuine, convergent fixes did land in the same span (a definition-meaning fix to sense 2, and an adaptation-note overclaim on **surrounded with** that both reviewers caught) — this is not a case of the reviewer being wrong about everything, only about this one field, repeatedly and inconsistently.

Rejected the round-4 complaint (and its restatement as a `consistency` issue) with a note citing the pattern, rather than rewording a fifth time. Style guide section 4's rule ("one reviewer flagging... is noise to reject") is written for a single round; this is the same signal compounding across rounds on one field, which the pipeline has no explicit stopping rule for yet. Not sizing a tooling fix from one entry, but a future lint pass should watch for the pattern: the same role, the same field, three or more rounds of unresolved blocking complaints on one entry, each with a different stated reason. If it recurs, `review_panel.py` could cap re-review rounds per field or flag repeat-field disputes for direct escalation instead of another panel call.

## [tooling] reviewer-a confused **one** with **won** in a pronunciation note, twice in one run

*Review run, 2026-09-21 (`20260921T063314Z-oqku5d`), `one-num` and its split-off `one-pron`.*

`one-num`'s pronunciation adaptation note reads "Pronounced *wʌn*, exactly like **won**, ... The **w** sound is not written." — correct: the headword is spelled `o-n-e`, with no `w` letter, though it carries an initial /w/ sound. reviewer-a flagged this as blocking, reasoning "the spelling begins with the letter w; the statement is false" — apparently reading the claim as being about **won** (which does begin with `w`) rather than **one** (the entry's actual headword). The identical note, carried over verbatim to the newly split `one-pron` entry, drew the same blocking complaint from reviewer-a a second time in the same run. Both rejected with the same reasoning; reviewer-b did not flag either.

Two occurrences of the same specific confusion (misreading which of two compared words a claim is about) in one run is not enough to size a fix, but is worth a note: a future run seeing this reviewer flag a claim about a headword's spelling is worth double-checking against the headword itself, not just the comparison word named alongside it.
